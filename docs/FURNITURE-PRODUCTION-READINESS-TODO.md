# WOODEX Furniture — production readiness and master to-do

**Decision: NO-GO for production or staging release.** This is the current prioritized implementation checklist for the independent Furniture application, not a claim that the project is complete. Baseline reviewed: `be30980d2e0930b1c2bdcf02f9c023c3e65085ce` plus this documentation update. Recheck status and evidence at every release candidate. `[x]` means only the specifically described preparation is done; `[ ]` includes partial, blocked and unverified work. Priorities: **P0** = foundation or release blocker; **P1** = required product capabilities; **P2** = conditional on agreed scope/provider/business decisions. P1/P2 are not permission to launch without them: agree an explicit launch scope, and disable/remove anything excluded.

## How to use and maintain this list

- Treat this file as the current navigation and release checklist; the detailed [Website Studio master plan](WOODEX-FURNITURE-WEBSITE-STUDIO-MASTER-PLAN.md) defines target behavior. Older audit/progress documents are historical evidence and may contain outdated status, draft approval steps or obsolete stack choices. Current founder preference is **save accepted edits and publish immediately**, not a mandatory extra publish step. Optional drafts for new/unlisted content must remain isolated.
- For every item, attach its commit, reproducible test commands/results, environment, owner and acceptance decision before checking it off. A preview, source file, screenshot or green build is not completion. Re-test the exact release candidate; a local/CI result is not Hostinger proof.
- Furniture and Woodex Interior have separate applications, domains, admin, data and credentials. Interior and `marketingwoodex-cloud/-marketingwoodex` are references only; do not alter the supplied reference or import Interior business data. Keep real data, credentials, build output and dependencies out of Git.
- Implementation is authorized in synthetic environments. Hostinger is a later phase: no deployment, real-data import, provider sends or cutover without the relevant explicit authorization. Keep 5174/5176 usable while migrating incrementally.

The checked CI intentionally uses `npx vite build`, not the upstream production script. Repair/replace scripts and add meaningful tests; do not claim these absent suites passed.
- Historical docs have stale claims (e.g. two-field-only home, no Livewire/CI and a mandatory publish step). This file supersedes those status claims; do not infer present readiness from their older checked boxes.
- Review covered routes, migrations, application directory, configuration, manifests, current plans, CI and the checks above. It is **not** a line-by-line security audit, a full inventory of every possible inherited feature, a host inspection or a guarantee that this list captures every issue discovered during implementation.

## 6. P0 — verification and release gates

- [ ] **R01** Database: against the actual supported MySQL/MariaDB version, test clean install, upgrades from realistic prior schema, indexes/FKs, transactions, concurrent changes, idempotency, retry/failure, backup, restore and rollback. SQLite CI is useful but insufficient. Confirm whether manual SQL means schema-only or approved data; export schema only from verified Furniture migrations and verify Laravel migration history matches.
- [ ] **R02** Data safety: identify and authorize actual Furniture sources, old storefront records/files and ownership before cleanup or import; classify, back up, rehearse mapping/import, deduplication, reconciliation, single-writer cutover and restore. Preserve revisions/media and verify counts; no Interior customer data. Prove rollback including writes after cutover.
- [ ] **R03** Security: threat model and independent review of roles/record isolation, ID enumeration, CSRF/XSS/SSRF/open redirects, rich content, iframe origin/source checks, upload processing, exposed files, rate limits, sessions, secrets, privacy/consent/retention and audit. Resolve findings or document accepted risk with sign-off.
- [ ] **R04** End-to-end browser tests across direct navigation and refresh, responsive widths, keyboard/screen reader, failure/offline/stale states, save/publish/restore, cross-origin embedded login, media, all launch-scope forms and commerce flows. Confirm the actual Arena embedded login with the founder; simulation alone is not proof.
- [ ] **R05** Run release-candidate performance/accessibility/SEO checks, crawler-visible raw HTML, sitemap and redirects, and realistic load/failure tests; define acceptable thresholds and document measured results. Establish monitoring, logs/alerts, retention and incident response.
- [ ] **R06** Verify actual Hostinger Business PHP/web and CLI versions/extensions, MySQL version, public document root, rewrite/HTTPS, domain/DNS/cookies, storage permissions, backup, cron, resource limits and any required runtime/build capability. Inspect target state and preserve existing files/data before any authorized installation. Keep private config/vendor/storage outside public web root where supported.
- [ ] **R07** Produce a reproducible, immutable artifact from an exact reviewed commit, with dependency and integrity metadata, tested deployment instructions, schema/migration status, backup and rollback/runbook, plus a safe owner-provisioning process. Never put secrets or customer records in a shared ZIP/SQL.
- [ ] **R08** With separate authorization, deploy only to verified isolated staging; test full launch scope, freshness, domain, TLS, permissions, scheduler, backups/restore and rollback with synthetic data. Record failures and remediation; re-run on exact release candidate.
- [ ] **R09** Obtain named business, technical and security sign-off, explicit production deployment/data/provider authorization and a cutover/rollback window. Only then deploy; perform smoke tests, monitoring and post-release reconciliation. Keep staging approval distinct from production approval.
