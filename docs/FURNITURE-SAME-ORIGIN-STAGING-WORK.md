# Same-origin Furniture staging integration — work in progress

The owner authorized a test on `staging.blackibex.net`; `woodexfurniture.pk` is the separate real website and is not a deployment target. This work prepares the GitHub branch, not a Hostinger action. It is not a complete application package and has not been deployed to Hostinger.

## Implemented foundation

- Laravel can optionally serve the built Reimagin HTML shell at its known storefront URLs on the same origin as `/storefront-api/*`, `/login`, Livewire and `/admin`. It is disabled by default using `FURNITURE_STOREFRONT_BUNDLE_ENABLED=false`. With the flag enabled, a missing shell returns 503. Unrelated routes are not swallowed. The existing synthetic admin landing flag still takes precedence for `/`.
- The shell comes only from the fixed private application file `storage/app/storefront-preview/index.html`, not a path from a request. HTML responses are marked no-store/noindex. The feature flag is not authentication. Staging requires independent whole-site access protection and synthetic data.
- `scripts/assemble-storefront-preview.mjs` creates a **new** output directory containing `public/assets`, `public/images`, `public/og-cover.jpg`, a disallow-all `robots.txt`, and a private `storefront-preview/index.html`. It rejects executable/unknown extensions and symlinks, never copies the source sitemap or rewrite file, and refuses to overwrite an existing output. This is only a storefront fragment, not an installable ZIP or a Hostinger-specific layout.
- GitHub CI builds the actual storefront, assembles the fragment, and tests it with Laravel in a disposable same-origin PHP/SQLite HTTP environment, including a nested URL, an asset, the homepage content API, admin redirect and unknown route. This is not Apache, MariaDB, an authenticated browser test, or proof of actual Hostinger compatibility.

## Remaining Hostinger and business validation

The candidate assembles Laravel, locked vendor dependencies, Laravel Vite assets and the storefront fragment into a layout intended to keep the app/config/storage outside the web root. The actual Hostinger rewrite/document-root arrangement, access protection, PHP, private paths, SQL import, owner setup, HTTPS and rollback still need host-side testing. This CI proof does not implement the complete Astro storefront, business platform or production SEO. Most inherited catalog, commerce and forms remain demo/partial; do not enter real orders or data. The open-access 5188 preview is not packaged.

## First staging candidate built and tested

[GitHub Actions run 44149141412](https://github.com/woodex420/furniture-os/actions/runs/44149141412) at commit `a4906e31206e7d8bb2247c51b9633733e445aa19` passed all jobs and produced `furniture-staging-candidate-a4906e31206e7d8bb2247c51b9633733e445aa19` (retained for 7 days). It contains `furniture-staging-candidate.zip`, matching `furniture-staging-mariadb.sql`, `INSTALL.txt`, `BUILD-INFO.txt` and `SHA256SUMS`. The SQL comes from the same run's MariaDB 10.5.29 round-trip. CI imported it into another disposable MariaDB, extracted the ZIP and exercised the assembled package with a synthetic owner in a real Chromium browser: login, Livewire lead search, homepage editing and the updated storefront all passed. Other jobs tested MySQL 8.4.7 and the existing PHPUnit suite. This evidence is not a test of Hostinger, HTTPS, Apache/LiteSpeed rules, the site's password protection or a complete business platform.

The ZIP is an experimental **restricted-staging candidate**, not a production release. Follow its `INSTALL.txt`: whole-site protection must remain effective when applying `.htaccess`, the private app must sit outside all web roots, and the SQL goes into a new empty staging database only. The CLI owner setup requires interactive SSH. Do not use real customer data, payments or external integrations. GitHub Actions artifacts expire; if the artifact is no longer available, rerun the workflow on the intended commit and use the matching files from that one successful run.
