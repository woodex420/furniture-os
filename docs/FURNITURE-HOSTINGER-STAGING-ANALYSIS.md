## Official hosting and security constraints

- Hostinger's Git integration deploys a selected repository/branch into a selected directory, which defaults to `public_html`, and can auto-deploy on updates. A Git success status is not a PHP build, migration, asset-build or application acceptance test. [Hostinger Git guide](https://support.hostinger.com/en/articles/1583302-how-to-deploy-a-git-repository)
- Hostinger says the root home directory generally is `public_html` and cannot be changed on its Web/WordPress/Cloud plans. Confirm the actual site and account constraints before choosing an application layout. [Hostinger root directory guide](https://support.hostinger.com/en/articles/1583494-what-is-the-path-to-your-website-s-root-home-directory-and-how-to-change-it)
- Laravel requires serving only its intended `public` entry point/assets, not the application root. Do not expose `.env`, `.git`, application source, storage, database backups or vendor through the web. If this plan fixes the document root, a private-app/public-entry arrangement requires explicit path configuration and real staging verification; do not assume uploading the whole repo under `public_html` or a blanket rewrite is safe. [Laravel deployment guide](https://laravel.com/docs/13.x/deployment)
- Laravel documents MariaDB 10.3+ support, but that alone does not establish compatibility with this app or with the actual host. [Laravel database guide](https://laravel.com/docs/13.x/database) MariaDB Foundation lists Community 10.5 end of maintenance as 24 June 2025. If the host really uses 10.5, ask Hostinger which security fixes it supplies or whether a maintained version is available; do not upgrade a shared database server without coordination and backups. [MariaDB maintenance policy](https://mariadb.org/about/#maintenance-policy)
- Project Composer requires PHP `^8.4.1`, a stricter minimum than Laravel's baseline. PHP web and CLI versions/extensions may differ. Test locked `composer check-platform-reqs`, PDO MySQL and the actual web runtime; 8.5 dependency compatibility and the installed Hostinger PHP have not been established. Do not change a live site's PHP version as an experiment.
- An external React API URL and CORS settings are not a drop-in solution: this project has a Laravel session/Livewire admin and a development-only storefront proxy. Separate domains would require a reviewed API contract, exact origins, HTTPS/session/cookie/CSRF behavior and a crawler-visible publishing strategy. A standalone Vite build is not the complete approved Astro storefront. No secrets belong in `VITE_` variables.

A SQL import and Laravel migrations are not interchangeable: test the exact installation path, and never re-run already-imported migrations or wipe an existing database. Test future additive migrations, backups and restore.
5. Establish a staging-only layout with the intended public files exposed and private app files outside the web root; configure HTTPS, owner provisioning and private environment values securely. Validate web assets, Livewire, direct routes, refreshed URLs, authentication, read/write permissions and rollback using synthetic data. `storage:link`, caches, scheduler and queues must be selected and tested for actual app/storage needs; don't execute generic commands against an unknown existing site.
6. Run a documented smoke/security/backup test and obtain acceptance before any production release. Keep the storefront and admin noindex and the staging instance access-controlled. Production cutover, real data and provider activation require a separate decision.
