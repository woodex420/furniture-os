# Furniture builder document foundation — experimental, not published

This is an experimental storage/contract foundation for the multi-page builder. A subsequent **fixed, synthetic-only** HTML proof is described below. Neither replaces the existing home, service, city or blog bridges; migrates existing pages; nor publishes the storefront. No records are seeded by application migrations. The final route registry, publishing strategy and general builder are still required.

## V1 contract

Laravel `BuilderDocumentV1` accepts a root with exactly `schema_version: 1` and `sections` (an ordered list of up to 10). A section has exactly `id`, `type`, and `props`; IDs are unique lowercase canonical v4 UUIDs. The only initial type is `article_text`, with exactly `summary` and `body` strings. These names match the actual Reimagin `ArticleText` component's props; TypeScript definitions in `src/pages-builder/furniture-document-v1.ts` express that compile-time relationship. Text is nonblank, valid UTF-8, limited to 300/12,000 Unicode characters, and encoded JSON is capped at 65,536 bytes. Text is retained as text, not interpreted as HTML. Empty section lists are allowed. Unknown versions, properties and section types are explicitly rejected rather than stripped. Types alone do not validate untrusted JSON; the Laravel contract is authoritative. Any future HTTP input must independently address request-size/depth limits and duplicate JSON object keys before decoding, and validate on the server.

This is deliberately narrow: it has no media, styling, links, layout nesting, route, SEO fields, catalogue data, page ownership or visibility. Adding them needs explicit schema versions/migration and shared renderer support. It is not a completed generic page model.

## Revisions and safety

`BuilderDocumentRevisions` is an internal service, used by the tightly restricted synthetic proof below but not a general HTTP API. It rechecks the current actor under lock against the owner workspace and storefront-edit gates, validates every document, serializes writes in a transaction, checks the expected revision and uses a conditional update, then appends a per-document version. Restore creates a new revision after validating its source; it cannot use another document's history. Corrupt/unsupported stored data is rejected rather than overwritten. A failed snapshot rolls back the content change. This is storage history, not publishing or proof of a concurrent database workload.

The additive migration creates two new empty tables. Rolling it back **drops all documents and versions stored in these tables**. Back up first; never roll back real data without a tested recovery plan. The current home, city, service and blog tables are untouched. MySQL/MariaDB CI tests exercise synthetic create/edit/restore and SQL roundtrip; they do not prove concurrent behavior or actual Hostinger compatibility. No automatic production deployment is performed.

## Section operation foundation

`BuilderSectionOperations` supplies pure, in-memory V1 article-text add, duplicate, move one position and remove operations. It validates the full input and result against the contract, requires a fresh valid section UUID for add/duplicate, preserves order and content, rejects unknown sections, invalid moves, duplicates, over-limit documents and out-of-bounds actions, and does not mutate the caller's input. The operations themselves do not authenticate, persist, publish or enforce future template-required slots. Any caller must separately authorize, generate cryptographically random v4 IDs, enforce required-slot rules and save through `BuilderDocumentRevisions` with the current expected revision. The local/testing-only synthetic proof now calls them through an owner-only form; the general builder and existing storefront remain unconnected.

## Synthetic save-to-HTML proof

A deliberately narrow experiment serves `/experiments/builder-html-proof` and an owner form at `/admin/website/builder-html-proof` **only** when `FURNITURE_BUILDER_HTML_PROOF_ENABLED=true` and `APP_ENV` is `local` or `testing`. Both are unavailable by default and in production/staging environments even with the flag on. The reader exposes one fixed document UUID containing a required fixed article-text section; the owner can add, edit, duplicate, reorder and remove other article-text sections within that document. There is no page-creation UI, route registry, arbitrary document lookup or visibility system. Do not put real data at those reserved IDs. If accidentally enabled in a publicly accessible local/testing installation, the synthetic reader is accessible without login: `noindex` is not access control. Use isolated infrastructure and synthetic data only.

The owner form uses Laravel's normal session, authorization, request forgery protection, rate limiter and revision conflict checks. Adding, duplicating, moving or removing a section saves immediately; these actions reload the page and discard any unsaved text in other forms, with an explicit warning. The original required section cannot be removed. Its accepted save commits the revision and the next uncached anonymous request renders from the database in section order with escaped text and no JavaScript dependency. Invalid or unsupported stored documents fail closed. An optional synthetic visual canvas previews unsaved text using the actual React article component, while the separate text forms remain the only save path. It does not expose restore, though the internal service can restore and the next request sees that version.

The Astro static experiment now dispatches the V1 section through `DocumentSections` to the **actual Reimagin `ArticleText` component**. Laravel's PHP-only proof uses a separate Blade counterpart, not React running in PHP. A shared expected-markup fixture checks both renderings for this one example; it is not a guarantee of visual parity, all input parity or a production component registry. The proof avoids a Node runtime on the serving path, but has not been tested on Hostinger. Laravel's body bound supplements rather than replaces web-server limits; normal input middleware trims text.

Synthetic CI tests cover owner save, invalid/stale writes, restoration, escaping, authorization, feature/environment gates, and a real browser with JavaScript disabled, including an anonymous fresh HTTP response after a save. The proof is marked `noindex, nofollow` and `no-store`, so it demonstrates crawler-readable initial HTML, **not search indexing, production cache invalidation, or immediate publishing of real storefront pages**. Laravel 13 accepts valid same-origin Fetch Metadata as well as CSRF tokens; the browser test rejects a session write missing both. No deployment was performed.

## Synthetic React canvas boundary

When the proof is enabled and `FURNITURE_STOREFRONT_CANVAS_URL` points to an explicitly trusted, separate storefront origin, the owner form embeds that origin in a sandboxed frame and sends only the fixed synthetic draft. The canvas runs `DocumentSections` and the real React `ArticleText` component, updates while typing, and can focus the corresponding section form. It has no direct data loading or write path; form submissions still use authorization, CSRF and revisions. Structural actions still save immediately and discard unsaved text. The parent checks both the configured origin and iframe window; the frame checks its parent window, the parent origin, message type and a bounded draft shape. Blank drafts are allowed for preview only; Laravel's strict server validation remains authoritative. No private credentials or production data should be entered; the configured storefront can read the synthetic draft. Without JavaScript the iframe is not navigated, and missing, same-origin or invalid configuration leaves the forms usable. Analytics are not initialized in this synthetic canvas mode. This is not a general visual builder, SSR, production publishing or a guarantee that a separately deployed storefront permits framing. The synthetic browser test exercises both origins, draft escaping, unsaved state, focus and forged/malformed messages in addition to the no-JavaScript write proof.

## Remaining before use

- Establish one route registry, conflict/collision handling, accessible typed component registry and shared renderer; connect actual Reimagin pages and the owner canvas.
- Design migration for the existing hero/media/tagline and all revisions, preserving identities and older clients; test isolated round trips and rollback before a cutover.
- Prove atomic accepted-save-to-visible publication and crawler-visible current HTML on the actual hosting model, including invalidation and rollback. No mandatory separate publish step for ordinary accepted edits.
- For any general API/controller, independently design feature gating, authorization, request forgery protection, rate and server-enforced request-size limits, audit/access rules, robust reads, concurrency tests and browser coverage. The isolated proof does not supply a general API.
- Add remaining templates, component types and visual controls; complete CRM and business modules separately. Passing unit tests does not mean the platform or builder is complete.
