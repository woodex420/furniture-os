# WOODEX Furniture platform — isolated foundation

**Not an installable release. Do not upload or expose this application.** This is an independent Furniture application foundation started from the official `laravel/laravel` 13.x skeleton at commit `a255d7688770af9713daff1439c47ff9bc6abd47`. The source package identifies itself as MIT in `composer.json`. The original skeleton archive SHA-256 is `87f746392b7d8c2f1590a12c4a7317b5823386a40dd69b1007756cfbac21d68f`. No Interior application source, users, databases, assets or configuration were copied into this directory. The earlier Interior-derived application remains in `../laravel-admin-source/` as an isolated reference, not this Furniture runtime.

## Current state

**Current project status and prioritized release checklist:** [`../../docs/FURNITURE-PRODUCTION-READINESS-TODO.md`](../../docs/FURNITURE-PRODUCTION-READINESS-TODO.md). Older notes below describe earlier foundation milestones; where they conflict, the current checklist and code take precedence.

- PHP requirement is `^8.4.1` with Livewire `^4.4`. The Composer lock was produced using constrained offline metadata and then updated for advisories; GitHub validation run `44025892478` passed the standard locked install, PHPUnit and Composer audit for that run's SHA. That is not a complete security review. There is no installed vendor tree in this source. See `../../docs/FURNITURE-OWNER-AND-LOCK-PROGRESS.md`.
- `/` intentionally returns 503 rather than pretending an unfinished storefront is live; only the explicitly enabled synthetic admin preview redirects its root to `/admin` (see the [project map](../../docs/FURNITURE-PROJECT-MAP-AND-PREVIEW.md)). `/admin` renders an in-progress shell behind session authentication and a provisional owner-only gate; dashboard metrics remain pending. Leads and Contacts have owner-only read/search/pagination and detail foundations, plus experimental feature-flagged create flows, not completed CRM workflows. Site Overview and private media provide a limited feature-flagged first-hero and tagline integration, with revision history; see `../../docs/FURNITURE-HOME-VISUAL-CANVAS.md` and `../../docs/FURNITURE-HERO-UPLOADED-MEDIA.md`. An interactive first-owner provisioning candidate exists but is not approved for Hostinger. Registration, other roles, account recovery and complete permission policies remain pending.
- A minimal session-authentication foundation and feature tests are present. The login form now uses WOODEX styling but remains a development foundation, not a release-ready authentication experience. Laravel's normal web CSRF middleware is retained; sign-in uses per-account/IP and aggregate-IP throttling, successful login rotates the session and logout invalidates it. Workspace/login responses are marked private/no-store and noindex. This is incomplete and **must not be exposed as an operational login**: full authentication/authorization, account lifecycle, rate-limit behavior across hosting, session security, real browser/HTTPS and security review are pending.
- `package-lock.json` covers the Vite/Tailwind assets. The shell reuses styles and icons from the approved standalone dashboard, with unavailable business features marked pending. The local build is not a release artifact, and visual fidelity and accessibility require continued review.
- A disposable native PHP 8.4.21/SQLite run passed the initial 17 tests / 152 assertions with the candidate-locked dependencies and PHPUnit 12.5.38, plus a localhost owner/non-owner CSRF smoke. The temporary PHP lacks `xmlwriter`, so Composer installation ignored that requirement and a modified PHPUnit entry point bypassed its extension check. This is partial experimental evidence, not a standard locked test or security acceptance. Later results and hosted runs are recorded in the progress documents.
- Laravel users/cache/jobs migrations, owner initialization and provisional customer read/write-candidate tables are **not a reviewed Furniture SQL export**. Only disposable local SQLite databases, synthetic accounts and synthetic customer rows were created; no Hostinger database, real accounts, SQL dump, credentials, real customer data or live integration were created.

## Before any distribution

Establish a complete native PHP/Composer test environment; review the candidate Composer lock and official advisories; build and test dependencies, auth, permissions and the actual UI; implement the requested business workflows, storefront and Livewire components; and pass synthetic MySQL and security checks. Only then build a versioned ZIP and, if requested, generate a reviewed SQL schema including consistent Laravel migration state from a disposable database. A host-created database name and username are hosting-specific: configure them privately on the server, never in Git, a shared ZIP or chat. See `../../docs/FURNITURE-PACKAGE-AND-MANUAL-DATABASE-PLAN.md`.
